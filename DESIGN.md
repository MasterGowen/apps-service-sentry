# Проектирование Sentry

## Цель

Преобразование минимального blueprint в полнофункциональное self-hosted решение Sentry с пятью контейнерами, соответствующее требованиям платформы автодеплоя.

## Компоненты

### Сервисы

1. **sentry-web** — основной сервис с пользовательским интерфейсом и API
   - Образ: `sentry:24`
   - Внутренний порт: 9000
   - Health check: `/api/0/health/`

2. **sentry-worker** — обработка очереди событий
   - Образ: `sentry:24`
   - Команда: `run worker`

3. **sentry-cron** — выполнение периодических задач
   - Образ: `sentry:24`
   - Команда: `run cron`

4. **postgres** — хранение метаданных и событий
   - Образ: `postgres:15-alpine`
   - Объём: `sentry-postgres`
   - Health check: `pg_isready`

5. **redis** — реализация очередей и кэширование
   - Образ: `redis:7-alpine`
   - Объём: `sentry-redis`
   - Health check: `redis-cli ping`

### Сети

- `platform_network` — внешняя сеть для интеграции с Caddy
- `sentry_internal` — внутренняя сеть для взаимодействия между сервисами

См. детали архитектуры: [ARCHITECTURE.md](ARCHITECTURE.md)

## Этапы реализации

1. Удаление `src/`, обновление `.gitignore`
2. Корректировка `service.yml`
3. Генерация `docker-compose.yml`
4. Настройка переменных окружения
5. Обновление документации

## Минимализм

### Включено

- PostgreSQL — для хранения метаданных
- Redis — для очередей и кэша
- Worker — для обработки событий
- Cron — для периодических задач

### Исключено

- Clickhouse — не требуется в минимальной конфигурации
- MemCached — избыточен (Redis выполняет те же функции)
- Kafka — избыточен для текущей нагрузки
- Relay — не требуется для внутреннего использования
- Nginx — не требуется (используется Caddy)

### Оценка ресурсов

- Оперативная память: 1.5–2 ГБ
- Дисковое пространство: 5–10 ГБ
- ЦП: минимальное использование (низкая нагрузка)
